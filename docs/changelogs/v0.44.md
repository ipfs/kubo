### 🔦 Highlights

#### 🆕 New repositories default to CIDv1

A new repository now defaults to CIDv1 (base32, starting with `bafy` or `bafk`) instead of CIDv0 (base58 `Qm...`). Both `ipfs init` and `ipfs daemon --init` apply the [`unixfs-v1-2025`](https://github.com/ipfs/kubo/blob/master/docs/config.md#unixfs-v1-2025-profile) import profile, so `ipfs add`, `ipfs files`, and the initial MFS root produce CIDv1 with raw leaves, 1 MiB chunks, and the other [IPIP-499](https://specs.ipfs.tech/ipips/ipip-0499/) settings. Run `ipfs init --profile unixfs-v0-2015` to start a new repository on those legacy values instead.

CIDv1 base32 is case-insensitive, works as an origin for subdomain gateways, and matches the CIDs produced by other IPFS implementations. New nodes get those properties without having to apply a profile by hand.

Existing repositories are left untouched: there is no migration and no repo-version bump, so a node that upgrades keeps producing the same CIDs as before. A repo whose UnixFS import settings are still implicit now prints a notice at daemon startup suggesting you pin a profile so its CIDs stay stable across releases: [`unixfs-v1-2025`](https://github.com/ipfs/kubo/blob/master/docs/config.md#unixfs-v1-2025-profile) for the modern defaults, or [`unixfs-v0-2015`](https://github.com/ipfs/kubo/blob/master/docs/config.md#unixfs-v0-2015-profile) to keep reproducing your existing CIDs. Applying either profile silences the notice.

Every import path follows the repo's config, not just `ipfs add`: `ipfs files`, the MFS root, the gateway, and the `github.com/ipfs/kubo/client/rpc` Go library all produce the configured CID version. `Unixfs().Add` in that library used to send its own defaults for CID version, chunker, hash, and DAG layout, which overrode the daemon's `Import.*` settings and could return different CIDs than `ipfs add` on the same node. It now sends only what the caller sets explicitly, and forwards the `MaxFileLinks`, `MaxDirectoryLinks`, and `MaxHAMTFanout` options that were previously dropped.

`ipfs add --cid-version=0` keeps producing dag-pb leaves, so a small file comes out as a `Qm...` CID rather than a raw `bafk...` leaf, even on a repo whose config enables raw leaves for CIDv1.

#### 📁 `ipfs ls` can print readable sizes and sort by size

Two new flags on `ipfs ls`, both off by default. `--human` (`-H`) prints sizes in SI units such as `3.0 kB` and `2.0 MB`, matching `ipfs repo stat -H`. `--sort-size` (`-S`) lists the biggest entries first, so you can find what fills a directory without piping through `sort`. Run `ipfs ls --help` for how they combine with `--stream`, `--size`, and the JSON response.
